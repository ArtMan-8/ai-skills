# Evals: technical-language-core

Набор из **100 независимых сценариев** в `cases.jsonl` и скрипт прогона `run_eval.py` для полной проверки: генерация ответов, слепая оценка и сборка сравнительной таблицы.

`partner-a`, `partner-b`, `partner-c` в поле `targets` — метки групп для отчёта. Фактически каждый кейс прогоняется для двух промптов: `ours` и `baseline`.

`run_eval.py` сравнивает промпт skill с нейтральным редакторским baseline.

## Если просят «запусти evals»

Агент выполняет одну команду, подставив свой раннер. Из корня репозитория:

```bash
cd skills/technical-language-core
python3 evals/run_eval.py \
  --runner-command '<раннер> --system {system_file} --prompt {prompt_file}'
```

По умолчанию `--workers 6`, `--timeout 300`. После завершения показывает `benchmark.md` и `benchmark.csv`.

## Наборы

- **40 кейсов `core`** — смысловая безопасность: модальность, условия, отрицания, числа, терминология, режимы работы, границы.
- **45 кейсов `strengths`** — расширенные сценарии технического текста, разбитые на три нейтральные группы:
  - `EXT-A-*` — 15 кейсов: процедурный текст, аудит, глоссарий, границы применимости;
  - `EXT-B-*` — 15 кейсов: сообщения об ошибках, отчёты, релизы, инструкции, формальные нормы;
  - `EXT-C-*` — 15 кейсов: естественность, штампы, клише, жанровые границы.
- **15 кейсов `language`** — `LANG-01…LANG-15` (14 английских, 1 смешанный): наш skill на английском и смешанном тексте — базовый английский пакет, модальность, номинализации, термины, процедуры, предупреждения, ошибки, пассив, единство терминов, смешанный текст, перевод по запросу, проверка.

## Запуск

`run_eval.py` не привязан ни к модели, ни к CLI. Он вызывает указанную команду и подставляет в неё два пути:

- `{system_file}` — файл с системным промптом;
- `{prompt_file}` — файл с запросом пользователя.

Раннер запускается в каталоге `<out>/workdir`; по умолчанию — `evals/evals-runs/<timestamp>/workdir`.

Команда должна напечатать ответ в stdout. Одна и та же команда используется для генерации и для судейства; скрипт не знает, какая модель или инструмент за ней стоит.

Если инструмент читает промпт из stdin, оберните вызов в shell явно:

```bash
--runner-command "sh -c 'your-llm --system {system_file} < {prompt_file}'"
```

Полный прогон. Из корня репозитория:

```bash
cd skills/technical-language-core
python3 evals/run_eval.py \
  --runner-command '<раннер> --system {system_file} --prompt {prompt_file}'
```

Всегда запускаются все 100 кейсов × 2 промпта: 200 генераций и 100 оценок. Частичных режимов, матриц и лимитов нет.

Результат по умолчанию: `evals/evals-runs/<timestamp>/` относительно каталога `technical-language-core`.

Главные файлы результата:

- `benchmark.md` — сравнительная таблица;
- `benchmark.csv` — те же итоги в CSV;
- `verdicts.csv` — вердикты по каждому кейсу и каждому skill;
- `benchmark.json` — агрегаты и строки;
- `raw/<skill>/<case>.txt` — ответы skill;
- `judge/<case>.json` — вердикты судьи;
- `prompts/` — собранные системные промпты;
- `run.json` — число задач.

## Что делает `run_eval.py`

1. Собирает два системных промпта:
   - `ours` — `SKILL.md` + русский каталог + английский пакет + терминология + исключения + примеры;
   - `baseline` — нейтральный редактор без skill.
2. Запускает каждую пару «кейс × промпт» через указанную команду в рабочем каталоге прогона.
3. Оценивает ответы слепо: варианты A и B перемешиваются, судья не знает, где какой промпт.
4. Считает PASS/FAIL/UNCERTAIN, критические ошибки, среднее качество и пишет таблицы.

## Зачем три набора

Кейсы `core` проверяют философию `technical-language-core`: сохранить смысл, не переписывать корректное, не выдумывать факты. Это основной набор для сравнения поведения.

Кейсы `strengths` проверяют более широкие требования к техническому тексту: процедуры, ошибки, отчёты, релизы, стиль и жанровые границы. Они сложнее кейсов `core` и не обязаны давать ту же долю PASS. **Не сравнивайте долю PASS между наборами напрямую** — это разные задачи и разные метрики.

Кейсы `language` проверяют, что skill работает на языке документа, не переносит русские нормы на английский, сохраняет термины и не переводит без запроса.

Рекомендуемые метрики отчёта:

| Метрика                                            | Что показывает                                                     | Где применять                            |
| -------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| Сохранение смысла (PASS/FAIL + критические ошибки) | модальность, условия, числа, термины, отсутствие выдумки           | во всех наборах как обязательный минимум |
| Формальные нормы процедурного текста               | длина предложений, пассив, номинализации, повелительное наклонение | `EXT-A-*`, `EXT-B-*`                     |
| Английский базовый пакет                           | 20/25 слов, простые времена, условие перед командой, термины       | `LANG-*`                                 |
| Естественность и отсутствие AI-штампов             | канцелярит, клише, ритм, обвязка чата                              | `EXT-C-*`                                |
| Стоимость и длина ответа                           | токены, время, многословие                                         | все наборы                               |

## Поля кейса

| Поле               | Значение                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| `id`               | `SEM-01`, `EXT-A-01`, `EXT-B-01`, `EXT-C-01`, `LANG-01` и т. д.                                                |
| `suite`            | `core` — смысловая безопасность; `strengths` — расширенные сценарии; `language` — английский и смешанный текст |
| `targets`          | `["ours"]` для `core` и `language`; `["partner-a"]`, `["partner-b"]` или `["partner-c"]` для `strengths`       |
| `lang`             | `ru`, `en`, `mixed`                                                                                            |
| `mode`             | `edit`, `check`, `write`, `evaluate`, `terminology`, `humanize`, `audit`                                       |
| `focus`            | что именно проверяет кейс                                                                                      |
| `prompt`           | запрос пользователя                                                                                            |
| `must`, `must_not` | семантические критерии                                                                                         |

Каждая пара «кейс × промпт» запускается в новом вызове раннера. `must` и `must_not` — семантические критерии, а не строки для буквального сравнения.

## Язык текста

Поле `lang` задаёт язык входного текста:

- `ru` — русский;
- `en` — английский;
- `mixed` — смешанный текст: фрагменты на разных языках; код, идентификаторы и имена не переводятся.

Наш skill поддерживает русский полностью и английский в объёме базового пакета. Для остальных языков действует только языково-нейтральное ядро.

## Важные оговорки

- Судья использует тот же раннер, что и генерация. Это не независимый человек; ключевые кейсы стоит проверять вручную.
- Доли PASS между наборами `core`, `strengths` и `language` напрямую не сравниваются: это разные задачи.
- Английский пакет — базовый набор правил контролируемого английского, не полный внешний стандарт.
- Результаты по умолчанию пишутся в `evals/evals-runs/` внутри skill; этот каталог внесён в `.gitignore`. Если задать `--out` в другое место, `raw/`, `judge/` и `benchmark.*` могут попасть в git — не коммитьте их, если не хотите хранить ответы.

## Если что-то сломалось

- `the following arguments are required: --runner-command` — передайте команду раннера.
- Команда раннера не запускается — проверьте шаблон и пути `{system_file}` / `{prompt_file}`.
- Ошибки кейсов — смотрите `raw/<skill>/<case>.err`.
- Судья не разобрал JSON — смотрите `judge/<case>.raw.txt`.
- Таймауты — увеличьте `--timeout` (по умолчанию 300 с), уменьшите `--workers`.
